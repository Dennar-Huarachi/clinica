### CU-01 — Iniciar y cerrar sesión

| Campo | Contenido |
|---|---|
| Caso de Uso | CU-01 Iniciar y cerrar sesión |
| Propósito | Permitir que los usuarios autentiquen su identidad en el sistema y finalicen su sesión de trabajo de forma segura. |
| Resumen | Este caso de uso valida la identidad del usuario a través de sus credenciales (nombre de usuario, correo o cédula de identidad, junto a su contraseña cifrada), diferenciando los canales de acceso entre pacientes y personal institucional. Si la autenticación es exitosa y la cuenta está activa, emite una credencial de acceso temporal en una cookie segura y permite consultar o revocar la sesión activa. Aplica controles de intentos fallidos por minuto y audita cada intento de acceso y salida en la bitácora (RN21). |
| Actores | Paciente, Médico, Recepcionista, Administrador (actores principales según su perfil), y el Sistema (actor secundario que valida credenciales, emite credenciales de sesión y audita eventos). |
| Actor iniciador | Cualquier usuario registrado (Paciente, Médico, Recepcionista o Administrador); para el inicio de sesión no se exige sesión previa, mientras que para el cierre y la verificación se requiere sesión activa. |
| Flujo del proceso | **Flujo básico (Inicio de sesión exitoso):**<br>1. Actor: Ingresa al portal de acceso, selecciona su perfil (paciente o personal) y proporciona su identificador (nombre de usuario, correo o cédula) y contraseña.<br>2. Sistema: Aplica control de tasa de intentos (máximo 5 solicitudes por minuto) y valida que los campos requeridos estén presentes y en formato adecuado.<br>3. Sistema: Busca la cuenta correspondiente, verifica que la contraseña coincida con el registro cifrado y confirma que la cuenta se encuentre en estado activo.<br>4. Sistema: Valida que el canal de acceso seleccionado corresponda al rol del usuario (paciente o personal institucional).<br>5. Sistema: Genera una credencial de sesión segura, registra la fecha y hora del último acceso y emite una cookie segura para el navegador.<br>6. Sistema: Registra el evento de inicio de sesión exitoso en la bitácora de auditoría.<br>7. Sistema: Retorna la información del usuario autenticado (datos personales, rol e identificadores clínicos vinculados) para habilitar las opciones del sistema.<br><br>**Flujo alterno A1 (Cierre de sesión):**<br>1. Actor: Solicita cerrar la sesión actual desde el menú de usuario.<br>2. Sistema: Valida la sesión activa a través de la credencial recibida.<br>3. Sistema: Invalida la credencial de acceso en el registro del usuario.<br>4. Sistema: Registra el evento de cierre de sesión en la bitácora de auditoría.<br>5. Sistema: Elimina la cookie de sesión del navegador y redirige a la pantalla de bienvenida.<br><br>**Flujo alterno A2 (Verificación de sesión activa):**<br>1. Actor: La aplicación del navegador solicita verificar el estado de la sesión activa al cargar una página.<br>2. Sistema: Valida la presencia y vigencia de la credencial de sesión.<br>3. Sistema: Retorna la información del usuario autenticado confirmando que la sesión está activa y válida. |
| Precondición | Para iniciar sesión: Contar con una cuenta previamente registrada en el sistema.<br>Para cerrar sesión o verificar: Poseer una sesión activa y una credencial válida. |
| Postcondición | Al iniciar con éxito: El usuario queda autenticado, se actualiza la fecha de último acceso, se emite la cookie de sesión y se registra el evento en bitácora con la acción "INICIO_SESION".<br>Al cerrar sesión: La credencial de sesión queda invalidada (nula), la cookie es destruida y se registra el evento en bitácora con la acción "CERRAR_SESION". |
| Excepciones | - Exceso de intentos de acceso superado (más de 5 solicitudes en un minuto) → "Demasiadas solicitudes. Por favor intente más tarde." → Código HTTP 429.<br>- Campo de tipo de acceso omitido en el formulario → "Debe indicar el tipo de acceso (paciente o personal)." → Código HTTP 422.<br>- Tipo de acceso con valor no admitido → "El tipo de acceso seleccionado no es válido." → Código HTTP 422.<br>- Identificador de usuario omitido → "Debe ingresar su usuario, correo o cédula de identidad." → Código HTTP 422.<br>- Identificador que excede el límite permitido → "El identificador no puede exceder los 100 caracteres." → Código HTTP 422.<br>- Contraseña omitida → "La contraseña es obligatoria." → Código HTTP 422.<br>- Usuario no encontrado o contraseña incorrecta → "Credenciales incorrectas o cuenta inactiva." (se registra "INTENTO_FALLIDO_SESION" en bitácora) → Código HTTP 401.<br>- Cuenta en estado diferente a activo (inactiva o bloqueada) → "Su cuenta se encuentra inactiva o bloqueada. Contacte a la administración." (se registra "INTENTO_SESION_CUENTA_INACTIVA" en bitácora) → Código HTTP 403.<br>- Cuenta de personal ingresando por la pestaña de pacientes → "Esta cuenta corresponde a personal clínico. Por favor ingrese por la pestaña \"Personal de la Clínica\"." (se registra "INTENTO_ACCESO_CANAL_INCORRECTO" en bitácora) → Código HTTP 403.<br>- Cuenta de paciente ingresando por la pestaña de personal → "Esta cuenta corresponde a un paciente. Ingrese desde el \"Portal Pacientes\"." (se registra "INTENTO_ACCESO_CANAL_INCORRECTO" en bitácora) → Código HTTP 403.<br>- Solicitud de cierre o verificación sin credencial o con sesión expirada → "Acceso no autorizado: se requiere un token de sesión válido" o "Sesión inválida o expirada. Por favor vuelva a iniciar sesión." → Código HTTP 401. |

### CU-02 — Cambiar contraseña

| Campo | Contenido |
|---|---|
| Caso de Uso | CU-02 Cambiar contraseña |
| Propósito | Permitir que cualquier usuario autenticado actualice su contraseña de acceso cumpliendo las políticas de seguridad institucional. |
| Resumen | Este caso de uso permite a cualquier usuario con sesión activa modificar sus credenciales de seguridad proporcionando su contraseña actual y una nueva que cumpla con los estándares de robustez (mínimo 8 caracteres, mayúsculas, minúsculas, números y símbolos especiales). Comprueba que la nueva clave no sea idéntica a la anterior, almacena la nueva clave cifrada de forma irreversible, desmarca la bandera de cambio obligatorio de contraseña y audita la modificación en la bitácora (RN21). |
| Actores | Cualquier usuario autenticado (Paciente, Médico, Recepcionista, Administrador) y el Sistema (valida políticas de complejidad, cifra la clave y audita el cambio). |
| Actor iniciador | El usuario autenticado (cualquiera de los roles: Paciente, Médico, Recepcionista o Administrador). |
| Flujo del proceso | **Flujo básico (Actualización exitosa de contraseña):**<br>1. Actor: Accede a la opción de cambio de contraseña, ingresa su contraseña actual, define la nueva contraseña y confirma la nueva contraseña.<br>2. Sistema: Aplica límite de intentos (máximo 10 solicitudes por minuto) y valida que la sesión del usuario sea válida.<br>3. Sistema: Valida que los tres campos estén presentes, que la confirmación coincida exactamente con la nueva contraseña y que la nueva contraseña cumpla con las reglas de complejidad (mínimo 8 caracteres, mayúscula, minúscula, dígito numérico y símbolo especial) y sea distinta a la actual.<br>4. Sistema: Comprueba que la contraseña actual ingresada coincida con la que se encuentra resguardada en el registro del usuario.<br>5. Sistema: Verifica que la nueva contraseña no coincida mediante cifrado con la contraseña anterior.<br>6. Sistema: Cifra la nueva contraseña, actualiza el registro del usuario y desmarca el indicador de cambio obligatorio de contraseña.<br>7. Sistema: Registra el evento de cambio de contraseña en la bitácora de auditoría.<br>8. Sistema: Confirma la actualización exitosa con el mensaje de confirmación al usuario. |
| Precondición | El usuario debe tener una sesión activa con credencial válida y conocer su contraseña actual. |
| Postcondición | La contraseña del usuario se actualiza cifrada, el indicador de cambio obligatorio pasa a falso, la fecha de actualización se renueva y se registra el evento en bitácora con la acción "CAMBIO_CONTRASENA". |
| Excepciones | - Límite de intentos superado (más de 10 solicitudes por minuto) → "Demasiadas solicitudes. Por favor intente más tarde." → Código HTTP 429.<br>- Usuario sin sesión o credencial expirada → "Acceso no autorizado: se requiere un token de sesión válido" → Código HTTP 401.<br>- Contraseña actual omitida → "La contraseña actual es obligatoria." → Código HTTP 422.<br>- Nueva contraseña omitida → "La nueva contraseña es obligatoria." → Código HTTP 422.<br>- Nueva contraseña con menos de 8 caracteres → "La nueva contraseña debe tener al menos 8 caracteres." → Código HTTP 422.<br>- Nueva contraseña idéntica a la actual (en validación inicial) → "La nueva contraseña no puede ser idéntica a la contraseña actual." → Código HTTP 422.<br>- Nueva contraseña sin mayúscula, minúscula, número o símbolo especial → "La nueva contraseña debe contener al menos una mayúscula, una minúscula, un número y un símbolo especial (!@#$%^&*(),.?\":{}|<>)." → Código HTTP 422.<br>- Confirmación de contraseña omitida → "Debe confirmar la nueva contraseña." → Código HTTP 422.<br>- Confirmación no coincide con la nueva contraseña → "La confirmación no coincide con la nueva contraseña." → Código HTTP 422.<br>- Contraseña actual incorrecta al verificar contra la base de datos → "La contraseña actual ingresada es incorrecta." → Código HTTP 422.<br>- Nueva contraseña coincide con el cifrado almacenado de la contraseña actual → "La nueva contraseña no puede ser idéntica a la contraseña actual." → Código HTTP 422. |

Evidencia: `backend/routes/api.php` + `backend/app/Http/Controllers/Paquetes/AccesoCuentas/CU02_CambiarContrasena/CambiarContrasenaControlador.php` + `backend/app/Http/Requests/Paquetes/AccesoCuentas/CU02_CambiarContrasena/CambiarContrasenaRequest.php` + `backend/app/Paquetes/AccesoCuentas/CU02_CambiarContrasena/CambiarContrasenaServicio.php` + `frontend/src/Paquetes/AccesoCuentas/CU02_CambiarContrasena/PaginaCambiarContrasena.jsx` (junto con `ModalCambiarContrasena.jsx`)  
Referencias: RF01, RN12, RN21

### CU-03 — Registrarse como paciente

| Campo | Contenido |
|---|---|
| Caso de Uso | CU-03 Registrarse como paciente |
| Propósito | Permitir que un nuevo paciente cree una cuenta en el sistema o vincule una cuenta de acceso a una ficha clínica previamente creada en recepción de la clínica. |
| Resumen | Este caso de uso permite a un paciente registrarse por autoservicio en el sistema sin requerir sesión previa. En una única transacción atómica, evalúa si la cédula de identidad ya existe: si es un nuevo paciente, crea su registro personal, su ficha clínica con código correlativo único de historia clínica, inicializa su expediente médico y genera su cuenta de usuario con rol paciente; si la cédula ya existía sin cuenta de usuario (registrada presencialmente en recepción), valida que los nombres y apellidos coincidan con la ficha registrada, actualiza sus datos de contacto y vincula la nueva cuenta de usuario a dicha ficha clínica sin duplicarla. Aplica límite de intentos (10 por minuto) y registra la auditoría (RN01, RN21). |
| Actores | Paciente (usuario no autenticado / visitante) y el Sistema (valida datos, asigna rol, genera código de historia clínica, emite credencial de acceso y audita la operación). |
| Actor iniciador | Paciente (visitante sin sesión activa en el sistema). |
| Flujo del proceso | **Flujo básico (Registro de paciente completamente nuevo):**<br>1. Actor: Ingresa al formulario de registro de paciente proporcionando cédula de identidad, nombres, apellidos, fecha de nacimiento, sexo, teléfono, correo electrónico, dirección (opcional), grupo sanguíneo (opcional), nombre de usuario y contraseña de acceso.<br>2. Sistema: Aplica control de tasa de solicitudes (máximo 10 por minuto) y valida que los campos requeridos cumplan formatos, longitudes y reglas de robustez de contraseña.<br>3. Sistema: Verifica que la cédula de identidad, el correo electrónico y el nombre de usuario no se encuentren previamente asociados a una cuenta de usuario activa.<br>4. Sistema: Constata que la cédula no existe en los registros de personas del establecimiento.<br>5. Sistema: Inicia una transacción y crea el registro de la persona con sus datos civiles y de contacto.<br>6. Sistema: Crea el registro del paciente generando un código correlativo único de historia clínica (formato con año y número correlativo) e inicializa su ficha médica preventiva vacía.<br>7. Sistema: Obtiene el identificador del rol de paciente y crea la cuenta de usuario con contraseña cifrada y estado activo.<br>8. Sistema: Genera la credencial de sesión inicial para permitir el acceso directo.<br>9. Sistema: Registra el evento en la bitácora de auditoría con la acción de autorregistro.<br>10. Sistema: Confirma la creación de la cuenta y retorna los datos del nuevo paciente autenticado.<br><br>**Flujo alterno A1 (Vinculación de cuenta a ficha clínica preexistente registrada en recepción):**<br>1. Actor: Ingresa al formulario de registro indicando su cédula y demás datos personales.<br>2. Sistema: Detecta que la cédula de identidad ya existe en los registros de personas de la clínica (por ejemplo, registrada en recepción).<br>3. Sistema: Comprueba que la persona registrada aún no disponga de una cuenta de usuario activa en el sistema.<br>4. Sistema: Compara los nombres y apellidos ingresados con los que figuran en la ficha clínica existente normalizando acentos y mayúsculas.<br>5. Sistema: Al validar la correspondencia, actualiza los datos de contacto (teléfono, correo y dirección) en la ficha preexistente y asocia la historia clínica existente.<br>6. Sistema: Crea la cuenta de usuario asociada a la persona con el rol de paciente y contraseña cifrada.<br>7. Sistema: Genera la credencial de sesión inicial.<br>8. Sistema: Registra el evento en la bitácora de auditoría con la acción de vinculación de cuenta de paciente.<br>9. Sistema: Confirma la vinculación exitosa y entrega el acceso al paciente. |
| Precondición | El paciente no debe contar con una cuenta de usuario activa asociada a su cédula de identidad, nombre de usuario o correo electrónico. |
| Postcondición | En paciente nuevo: Se crea el registro de persona, la ficha de paciente con código único de historia clínica, el registro de información médica inicial y la cuenta de usuario con rol paciente en estado activo. Se emite credencial de sesión y se registra el evento en bitácora con la acción "AUTORREGISTRO_PACIENTE".<br>En paciente preexistente: Se actualizan los datos de contacto de la persona existente, se preserva su historia clínica y se le asocia la nueva cuenta de usuario con rol paciente. Se emite credencial de sesión y se registra el evento en bitácora con la acción "VINCULAR_CUENTA_PACIENTE". |
| Excepciones | - Límite de intentos superado (más de 10 solicitudes por minuto) → "Demasiadas solicitudes. Por favor intente más tarde." → Código HTTP 429.<br>- Cédula de identidad ya asociada a una cuenta de usuario activa → "La cédula de identidad ya se encuentra registrada con una cuenta de usuario activa." → Código HTTP 422.<br>- Correo electrónico ya registrado en el sistema → "El correo electrónico ya se encuentra registrado." → Código HTTP 422.<br>- Nombre de usuario ya registrado en el sistema → "El nombre de usuario ya está en uso. Elija otro." → Código HTTP 422.<br>- Campos obligatorios omitidos (nombres, apellidos, fecha de nacimiento, sexo, teléfono, correo, nombre de usuario o contraseña) → "Los datos proporcionados no son válidos" (con lista de campos requeridos) → Código HTTP 422.<br>- Sexo con valor distinto a 'M' o 'F' → "Los datos proporcionados no son válidos" → Código HTTP 422.<br>- Contraseña con longitud menor a 8 caracteres → "La contraseña debe tener al menos 8 caracteres." → Código HTTP 422.<br>- Contraseña sin requisitos de complejidad (mayúscula, minúscula, número o símbolo especial) → "La contraseña debe contener al menos una mayúscula, una minúscula, un número y un símbolo especial (!@#$%^&*(),.?\":{}|<>)." → Código HTTP 422.<br>- Cédula existente en recepción cuyos nombres o apellidos no coinciden con los ingresados → "Los datos personales ingresados no coinciden con la ficha clínica registrada para este documento de identidad. Acérquese a recepción." → Código HTTP 422.<br>- Falla general o de transacción durante el registro → "Error al registrar paciente: <detalle>" → Código HTTP 400. |

### CU-04 — Administrar usuarios y roles

| Campo | Contenido |
|---|---|
| Caso de Uso | CU-04 Administrar usuarios y roles |
| Propósito | Permitir que el Administrador gestione integralmente las cuentas de usuario, sus roles y la matriz modular de permisos granulares del sistema. |
| Resumen | Este caso de uso proporciona al Administrador las herramientas para listar, buscar, crear y actualizar cuentas de usuario del personal clínico y administrativo, asignando credenciales y roles. Permite crear nuevos roles y gestionar la matriz de permisos por módulos funcionales asignando y revocando permisos de forma dinámica. Además, permite alternar el estado activo o inactivo de los usuarios resguardando que nunca se inhabilite ni degrade al último administrador activo del sistema, y audita cada operación de usuario o permisos en la bitácora (RN12, RN21). |
| Actores | Administrador (actor principal que gestiona las cuentas y permisos) y el Sistema (actor secundario que valida reglas de negocio, sincroniza permisos y registra bitácora). |
| Actor iniciador | Administrador (exigido por la regla de autorización de rol de la ruta). |
| Flujo del proceso | **Flujo básico (Creación de un nuevo usuario):**<br>1. Actor: Ingresa al módulo de usuarios y roles, presiona la opción para crear usuario y completa cédula de identidad, nombres, apellidos, correo, teléfono (opcional), rol institucional, nombre de usuario y contraseña inicial.<br>2. Sistema: Valida que la sesión sea de un administrador y verifica el cumplimiento de las reglas del formulario.<br>3. Sistema: Comprueba que el nombre de usuario y el correo no existan previamente.<br>4. Sistema: Verifica si la cédula ya existe en los registros de personas; si existe y ya posee usuario vinculado rechaza la operación; si no tiene usuario, asocia la persona existente; de lo contrario crea la nueva persona.<br>5. Sistema: Crea la cuenta de usuario con la contraseña cifrada, marca la bandera de cambio obligatorio de contraseña en el primer inicio y asigna el estado seleccionado.<br>6. Sistema: Si el rol asignado es médico y aún no cuenta con registro profesional, genera de forma automática su ficha médica con un número de matrícula basado en su documento.<br>7. Sistema: Registra el evento de creación de usuario en la bitácora de auditoría.<br>8. Sistema: Retorna la confirmación de usuario creado satisfactoriamente.<br><br>**Flujo alterno A1 (Edición y actualización de datos de usuario):**<br>1. Actor: Selecciona un usuario existente y modifica sus datos personales, correo, rol, estado o define una nueva contraseña de restablecimiento.<br>2. Sistema: Valida los datos recibidos y comprueba que el nuevo nombre de usuario o correo no pertenezcan a otro usuario.<br>3. Sistema: Verifica la regla de protección del administrador: si el usuario a modificar es el único administrador activo, bloquea cualquier intento de cambiarle el rol o cambiar su estado a inactivo.<br>4. Sistema: Actualiza los datos de la persona y de la cuenta de usuario (si se ingresó nueva contraseña, se cifra y se activa el indicador de cambio obligatorio).<br>5. Sistema: Registra la actualización en la bitácora de auditoría indicando los valores anteriores y los nuevos.<br>6. Sistema: Confirma la actualización exitosa.<br><br>**Flujo alterno A2 (Alternar estado de usuario - baja lógica / reactivación):**<br>1. Actor: Solicita activar o desactivar una cuenta de usuario desde el listado.<br>2. Sistema: Localiza la cuenta de usuario.<br>3. Sistema: Si el usuario es administrador y se intenta desactivar, valida que exista al menos otro administrador activo en el sistema; de lo contrario, bloquea la acción.<br>4. Sistema: Invierte el estado de la cuenta (de activo a inactivo, o de inactivo a activo).<br>5. Sistema: Registra el cambio de estado en la bitácora de auditoría.<br>6. Sistema: Retorna el nuevo estado de la cuenta confirmado.<br><br>**Flujo alterno A3 (Gestión de roles y sincronización de matriz de permisos):**<br>1. Actor: Accede a la pestaña de roles y permisos, selecciona un rol o registra uno nuevo con nombre y descripción.<br>2. Sistema: Al crear un nuevo rol, valida que el nombre sea obligatorio y que no exista otro rol con la misma denominación; luego lo crea y audita el evento.<br>3. Sistema: Despliega la matriz de permisos agrupados por módulos funcionales indicando cuáles están asignados al rol.<br>4. Actor: Modifica la selección de permisos granulares marcando o desmarcando casillas y pulsa guardar cambios.<br>5. Sistema: Valida los identificadores de permisos contra el catálogo del sistema, reemplaza las asignaciones del rol en una transacción y audita la sincronización en la bitácora.<br>6. Sistema: Confirma que los permisos del rol han sido sincronizados correctamente. |

### Discrepancias

1. **CU-01 — Iniciar y cerrar sesión**:
   - **Qué dice la documentación:** En el documento `casos-de-uso-citas-medicas-vida-salud-v3.md` (sección 7, CU-01) se indica únicamente que el usuario ingresa nombre de usuario o correo y contraseña, sin detallar la existencia de canales diferenciados.
   - **Qué hace el código:** El código real exige obligatoriamente el parámetro `tipo_acceso` ('paciente' o 'personal'). Si un usuario con rol paciente intenta ingresar por el canal de personal o viceversa, el backend rechaza la petición con código HTTP 403 e instruye a ingresar por la pestaña correspondiente. Además, el código permite ingresar utilizando el número de cédula de identidad (`ci`), y la ruta implementa limitador de tasa de 5 intentos por minuto (`throttle:5,1`).
   - **Archivo:** `backend/app/Http/Requests/Paquetes/AccesoCuentas/CU01_IniciarCerrarSesion/IniciarSesionRequest.php`, `backend/app/Paquetes/AccesoCuentas/CU01_IniciarCerrarSesion/IniciarCerrarSesionServicio.php`, `backend/routes/api.php`.

2. **CU-03 — Registrarse como paciente**:
   - **Qué dice la documentación:** En las alternativas de CU-03 de `casos-de-uso-citas-medicas-vida-salud-v3.md` se señala que al detectar una ficha existente sin cuenta previa (creada en recepción), el sistema compara además del CI la fecha de nacimiento y el teléfono para validar la identidad y vincular la cuenta.
   - **Qué hace el código:** En `RegistrarsePacienteServicio.php`, la validación de coincidencia de identidad compara los nombres y apellidos ingresados contra los de la persona existente usando una función de normalización ortográfica. No compara la fecha de nacimiento ni el teléfono; al coincidir nombres y apellidos, procede a actualizar el teléfono, correo y dirección en la ficha preexistente y vincula la nueva cuenta de usuario. Asimismo, la ruta implementa limitador de tasa de 10 intentos por minuto (`throttle:10,1`).
   - **Archivo:** `backend/app/Paquetes/AccesoCuentas/CU03_RegistrarsePaciente/RegistrarsePacienteServicio.php`.

3. **CU-04 — Administrar usuarios y roles**:
   - **Qué dice la documentación:** En las reglas de seguridad de CU-04 de `casos-de-uso-citas-medicas-vida-salud-v3.md` se indica que "reactivar a un médico exige que su ficha médica en CU-08 esté activa con al menos una especialidad (RN04)".
   - **Qué hace el código:** En `AdministrarUsuariosRolesServicio.php`, la operación de alternar estado no verifica especialidades médicas ni el estado en la tabla de médicos; únicamente protege que no se desactive al último administrador activo del sistema. Adicionalmente, al crear un usuario con rol médico, el servicio genera automáticamente su registro en la tabla de médicos con matrícula profesional provisional por defecto si no existía.
   - **Archivo:** `backend/app/Paquetes/AccesoCuentas/CU04_AdministrarUsuariosRoles/AdministrarUsuariosRolesServicio.php`.

4. **CU-26 — Generar y restaurar copias de seguridad**:
   - **Qué dice la documentación:** En la ficha técnica de CU-26 de `casos-de-uso-citas-medicas-vida-salud-v3.md` solo se detallan las rutas API `GET /administracion/backups` y `POST /administracion/backups`.
   - **Qué hace el código:** El código implementa las rutas bajo `/api/seguridad/backups` (manteniendo `/administracion/backups` como alias de compatibilidad) y añade formalmente los endpoints transaccionales `GET /api/seguridad/backups/{id}/descargar` para descarga directa del archivo SQL y `POST /api/seguridad/backups/{id}/restaurar` para la restauración (con control de tasa `throttle:5,1`).
   - **Archivo:** `backend/routes/api.php`, `backend/app/Http/Controllers/Paquetes/AccesoCuentas/CU26_GenerarRestaurarCopiasSeguridad/GenerarRestaurarCopiasSeguridadControlador.php`.
